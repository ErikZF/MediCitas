# Data model: dictionary and normalization

**English** · [Español](data-model.es.md)

The relational model of Stage 1: every table and column with its meaning, the
normalization up to third normal form step by step, and the places where the model
departs from it on purpose, with the reason. The picture is the
[ER diagram](database.md#entity-relationship-diagram); how isolation between clinics
works is in [database.md](database.md) and [multitenancy.md](multitenancy.md).

## Overview

Four PostgreSQL 18 databases, one per service (database per service). 17 tables:

| Database | Owner | Tables |
| --- | --- | --- |
| `clinics_db` | clinics-service | `clinic`, `specialty`, `service` |
| `users_db` | users-service | `role`, `app_user`, `professional`, `professional_specialty`, `patient`, `outbox` |
| `appointments_db` | appointments-service | `working_hours`, `schedule_block`, `professional_service`, `appointment`, `clinical_note`, `outbox`, `idempotency_keys` |
| `logs_db` | audit-service | `audit_log` |

### Conventions

- **Identifiers** are `uuid` generated by the database with `uuidv7()`. Version 7 starts
  with a timestamp, so new rows land at the end of the B-tree instead of at random pages
  (version 4); no sequence has to be shared between services; and an id can be shown to a
  client without revealing how many rows exist.
- **Tenant tables** have the primary key `(clinic_id, <entity>_id)`, with `clinic_id`
  first. It keeps each clinic's rows together in every index, it is the column RLS filters
  on, and a foreign key that includes it cannot point to a row of another clinic.
- **Instants** are `timestamptz` (stored in UTC). **Times of the week** (`working_hours`)
  are `time` in the clinic's local time, because "Monday 08:00" must stay 08:00 when the
  clocks change; the clinic's `time_zone` turns them into instants.
- **Logical deletion**: `is_active` on clinics, services, users and professionals. Their
  appointments and audit entries keep pointing to them.
- **No foreign keys across databases.** A column marked **LR** (logical reference) holds
  the id of a row in another database; the service that writes it checks that the row
  exists, through the owning service's API. Why: [database.md, section 3](database.md#3-referential-integrity-in-microservices).
- **Row-level security** is enabled and forced on every table that has a `clinic_id`.
  Which role reads or writes what: [database.md, section 4](database.md#4-row-level-security-rls--multi-tenancy).

Key column legend: **PK** primary key, **FK** foreign key in the same database, **UQ**
unique, **LR** logical reference to another database.

## Normalization

### Functional dependencies of the domain

The rules of the statement, written as dependencies (→ reads "determines"):

- A clinic: `clinic_id → identifier, name, time_zone, is_active`; `identifier → clinic_id`.
- A specialty: `specialty_id → name`; `name → specialty_id`.
- A service: `(clinic_id, service_id) → specialty_id, name, duration_minutes, is_active`;
  `(clinic_id, name) → service_id`.
- A user: `app_user_id → keycloak_sub, clinic_id, role_code, is_active`;
  `keycloak_sub → app_user_id`. A role: `role_code → description`.
- A professional: `(clinic_id, professional_id) → app_user_id, full_name, is_active`;
  `(clinic_id, app_user_id) → professional_id`. Specialties and services are
  multi-valued: a professional has several of each.
- A patient: `(clinic_id, patient_id) → identification, full_name, birth_date, phone, email`;
  `(clinic_id, identification) → patient_id`.
- An appointment: `(clinic_id, appointment_id) →` professional, patient, service,
  `starts_at`, `duration_minutes`, status and its history fields. Also
  `starts_at, duration_minutes → ends_at`.
- A note: `(clinic_id, clinical_note_id) → appointment_id, content, ...`;
  `(clinic_id, appointment_id) → clinical_note_id` (one note per appointment).

### First normal form

Every column holds one value, and no table has repeating groups.

- **Working hours** are one row per block (`weekday`, `start_time`, `end_time`), not an
  array or a "Monday: 08-12, 13-17" text. That is what lets an `EXCLUDE` constraint forbid
  overlapping blocks and RF7 read a single day.
- **Specialties of a professional** and **services of a professional** are their own
  tables (`professional_specialty`, `professional_service`), not lists in `professional`.
- **Contact data** are separate columns (`phone`, `email`), one value each.
- **Status** is one value; its history is in separate columns (`status_changed_at`,
  `status_changed_by`, `cancel_reason`, `cancelled_by`) and in the chain of
  `rescheduled_from_id`, not in a list.
- Every table has a primary key, so no row is duplicated.

The only non-atomic columns are `outbox.payload` and `idempotency_keys.response_body`
(`jsonb`). They are messages, not domain data: they are written once, read whole by the
relay or returned whole to the client, and never queried by their attributes. The audit
fields of a `payload` become proper columns once they reach `audit_log`.

### Second normal form

No non-key column may depend on only part of a composite key. Every tenant table has the
key `(clinic_id, <entity>_id)`, so the question is whether something depends only on
`clinic_id` or only on the entity id.

- **Only on `clinic_id`**: nothing. The clinic's own data (`name`, `time_zone`) lives in
  `clinic` and is not repeated in any table: appointments-service asks clinics-service for
  the time zone instead of storing it next to the appointments.
- **Only on the entity id**: a UUID v7 is unique in practice, so `appointment_id` alone
  would identify the row. But the database only enforces uniqueness of the pair, and the
  pair is what makes composite foreign keys keep a child in its parent's clinic
  (`clinical_note (clinic_id, appointment_id) → appointment`). With the pair as the key,
  every other column depends on the whole key.
- **`professional_specialty`** is all key: nothing to check.
- **`professional_service`** has the key `(clinic_id, professional_id, service_id)`, and
  `specialty_id` depends only on `service_id`. **This is the one place that breaks 2NF, on
  purpose**: it is explained [below](#deliberate-departures).

### Third normal form

No non-key column may depend on another non-key column.

- **`service.duration_minutes`** stays in `service`, the only place that defines it.
  `appointment.duration_minutes` is not a copy of it but a different fact: the length
  the appointment was booked with. If the clinic later changes the service to 45
  minutes, existing appointments keep their 30 (I4). The same way an invoice line keeps
  the price it was sold at.
- **Role descriptions** are in `role`; `app_user` only holds `role_code`.
- **Specialty names** are in `specialty`; services and professionals point to it.
- **A professional's name** is in `professional`, not repeated in appointments or
  agendas, which carry only the `professional_id`.
- **A patient's contact data** are only in `patient`. Appointments and the audit log hold
  only the `patient_id`.
- Three columns do depend on other non-key columns, on purpose:
  `appointment.ends_at` (on `starts_at` and `duration_minutes`),
  `clinical_note.professional_id` and `clinical_note.appointment_status` (on the
  appointment the note belongs to). Explained [below](#deliberate-departures).

**Boyce-Codd.** Besides the primary keys, the determinants are `clinic.identifier`,
`specialty.name`, `(clinic_id, name)` of `service`, `app_user.keycloak_sub`,
`(clinic_id, app_user_id)` of `professional`, `(clinic_id, identification)` of `patient`
and `(clinic_id, appointment_id)` of `clinical_note`. Each one is declared `UNIQUE`: they
are candidate keys, so those tables are also in BCNF.

## Deliberate departures

Every place where the model stores something it could derive, with the reason and what
keeps it consistent.

| Where | What it repeats | Why | What keeps it consistent | Cost |
| --- | --- | --- | --- | --- |
| `appointment.ends_at` | `starts_at + duration_minutes` | The exclusion constraints that hold I1 and I2 need the interval as an expression over columns of the row, and the queries of RF7, RF8 and RF20 compare the end directly instead of recomputing it in every row. | `CHECK (ends_at = starts_at + make_interval(mins => duration_minutes))`: the engine rejects any row where it differs. | 8 bytes per appointment. |
| `professional_service.specialty_id` | `service.specialty_id`, which lives in another database | The service and its specialty live in clinics_db. Copying the specialty when the association is made lets availability and booking (RF7-RF9) check "this professional can still provide this service" inside appointments_db, in the same transaction, without calling clinics-service. If the clinic later changes the specialty of the service, the stored value no longer matches and the association stops offering slots until it is made again, which checks again that the professional has the new specialty (RF4). | The association is written only by the service that checks the specialty against users-service; booking and availability compare it with the service's current specialty. | A stale association offers no slots until an administrator renews it. |
| `clinical_note.professional_id` | `appointment.professional_id` | RLS lets a professional read only their own notes. With the author in the note, the policy is `professional_id = app_current_professional_id()`, a plain comparison on the row. Without it, the policy would need a subquery on `appointment` for every note read. | The service writes it from the appointment, in the same transaction that checks the caller is that appointment's professional; the policy rejects an insert with another professional. | 16 bytes per note. |
| `clinical_note.appointment_status` | `appointment.status` at the time of the note | Records in the row the rule "only attended appointments have a note" and the state the appointment was in when the note was written. | `CHECK (appointment_status = 'attended')`, and the service writes the note only after reading the appointment as `attended`, in the same transaction. An attended appointment never changes status again (RF13). | Adds no information the appointment does not have; it documents the rule where the note is. |
| `audit_log.patient_id` with `resource = 'patient_contact'` | `resource_id`, which is the same patient | The log has one shape for every entry, so RF19 filters by patient with one index for notes and contact data alike. | The relay validates every event before inserting it. | 16 bytes per contact entry. |

### Other decisions that are not normalization

- **No foreign keys across databases.** Each service owns its database; a reference to
  another service's row is checked through that service's API when it is written. A
  foreign key could not span two PostgreSQL databases, and keeping them together would
  undo the separation between services. The cost is that a row deleted elsewhere would
  leave a dangling id; the entities other databases point to (clinics, services, users,
  professionals, patients) are never physically deleted, only deactivated, so that does
  not happen.
- **`audit_log` has no foreign keys even in its own database.** It is history: an entry
  must survive whatever happens to the note, the patient or the user it names.
- **`specialty` is global, not per clinic.** "Cardiology" means the same in every
  clinic, and a global list lets the platform keep one catalog. It is the only domain
  table without `clinic_id`, and nothing in it is private to a clinic.
- **`clinic_id` in every key, even where the entity id would suffice**: see second normal
  form above. It is redundant in theory (a UUID v7 does not repeat) and is what makes
  isolation and composite foreign keys work.
